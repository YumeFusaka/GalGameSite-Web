# 前端样式系统整体重构设计

## 概述

这次重构保留项目现有的 Galgame 二次元粉色系与毛玻璃视觉气质，但会重新建立前端样式系统，让整站从“各页面分别写样式”提升为“同一套视觉语言下的统一产品”。本次改造的首要目标是提升全站移动端可用性与响应式表现，同时保证桌面端的质感、统一性和层次感不下降。

重构范围覆盖当前前端所有主要页面，包括布局层、首页、登录页、活动页、决议页、成员页，以及这些页面依赖的共享样式结构。本次也会同步整理样式命名、书写顺序和组织方式，避免后续继续在当前杂乱基础上叠加。

## 目标

- 保留当前偏二次元的粉色主视觉识别度。
- 保留半透明毛玻璃质感，但改为统一、可复用的表现方式。
- 让移动端和平板端成为真正的一等布局，而不是单纯把桌面页面缩小。
- 提升桌面端页面的统一性、节奏感和视觉层级。
- 建立清晰的样式架构，包括设计变量、布局原语和共享面板样式。
- 统一组件内部样式命名、书写顺序和响应式规则组织方式。

## 非目标

- 不做整站品牌重塑，不改成完全不同的视觉风格。
- 不做与本次视觉系统无关的大规模功能重写。
- 不强行引入过重的外部 CSS 方法论来破坏现有 Vue 组件结构。
- 不为了“重构而重构”，只在有助于响应式和样式清晰度时调整组件结构。

## 当前问题

### 全局样式层

- 当前全局 reset 过于薄弱，不能为页面提供稳定的布局基础。
- 响应式适配过度依赖缩小根字号，而不是让布局本身变化。
- 颜色、阴影、圆角、毛玻璃背景等规则在多个页面中重复硬编码。

### 布局与导航层

- 头部使用固定定位，导致页面内容需要各自手动避让顶部空间。
- 导航是明显的桌面端写法，在移动端没有真正的交互降级方案。
- 页面横向留白和主内容宽度由各页面单独控制，缺少统一容器系统。

### 页面模式层

- 首页、列表页、登录页分别维护自己的间距、背景和面板规则，整体割裂。
- 活动页和决议页结构相近，但样式实现重复且命名不统一。
- 多列布局在小屏上缺乏稳定折叠策略，容易产生拥挤或可读性下降的问题。

### 样式可维护性

- 类名大量使用 `box`、`space`、`info` 这类语义弱的名称，可读性差。
- 组件内样式顺序不固定，阅读和修改成本高。
- 部分选择器范围过宽，削弱了组件边界。
- 对第三方组件的样式覆盖缺乏集中约束，后续维护容易失控。

## 设计方向

这次改造不会把项目改成“极简商务风”，而是保留现在的粉色高光、通透面板、明亮头图和轻甜氛围。变化点不在于风格换掉，而在于把现有风格做成一套有规则的系统。

当前的问题不是“方向错了”，而是“同一个方向没有被系统化表达”。因此本次会通过少量稳定的视觉变量、共享面板样式和统一布局骨架，把首页、列表页、登录页和头部导航收拢到同一个设计系统中。

## 样式系统架构

### 1. 全局设计变量

建立一层共享变量，统一管理以下内容：

- 品牌主粉、强调粉、辅助浅粉、基础中性色。
- 主文本、次文本、弱化文本、反色文本。
- 毛玻璃背景、边框、阴影层级、模糊强度。
- 通用圆角等级。
- 通用间距刻度。
- 页面最大宽度、断点和响应式容器留白。
- 顶部导航高度与层级关系。

这些变量会成为页面和组件样式的唯一基础来源，减少散落的硬编码值。

### 2. 基础层与 Reset

当前全局样式会升级为更完整的基础层，至少覆盖：

- `box-sizing`
- `html`、`body`、`#app` 的高度与背景基础
- 图片默认表现
- 按钮、输入框的字体继承
- 链接默认样式
- 必要的列表重置
- 更稳定的字体渲染与页面基础背景

这一层的目标是提高布局可预期性，而不是和组件 scoped 样式冲突。

### 3. 布局原语

建立一组可复用的布局原语，例如：

- 页面外壳
- 内容主容器
- 通用 section 间距
- 响应式栅格包装层
- 通用玻璃态面板外壳

核心原则是：相同语义的页面空间不再由每个页面自己发明一套 margin，而是统一通过共享容器和 section 规则控制。

### 4. 共享视觉表面

建立少量可复用的视觉表面类型，例如：

- 头图区块表面
- 标准玻璃态面板
- 高亮卡片
- 紧凑型信息面板

这些表面将用于首页推荐块、活动预览、决议预览、登录卡片、成员列表容器等区域，使不同页面有统一的“材质感”。

## 响应式策略

本次改造以移动端和响应式体验为第一优先级，主要通过布局变化来适配，而不是单纯缩小字体。

### 断点意图

- 手机端：单列优先、导航收纳、触控友好、留白适中。
- 平板端：减少横向空白，允许适度多列，但避免密度过高。
- 桌面端：保留更完整的多列布局、悬浮效果和更丰富的视觉节奏。

### 响应式规则

- 用统一的最大宽度容器和流式左右内边距替换固定大 margin。
- 双栏和多栏内容在中小屏自动折叠为单列。
- 顶部导航切换为抽屉式或折叠式移动端交互。
- 避免不必要的固定卡片高度，优先保证内容自然流动。
- 在合适位置使用 `clamp()` 等方式控制标题、间距和头图高度的弹性。

## 布局重构

### 站点布局层

布局层将成为页面骨架的唯一管理者：

- 头部高度通过全局变量统一定义。
- 主内容顶部偏移由 layout 统一负责，而不是每个页面自己写 `margin-top`。
- 背景图和页面壳体的使用由 layout 统一控制。
- 页面内容统一落在共享容器规则中。

这样可以消除当前“头部固定，页面各自避让”的耦合问题。

### 顶部导航层

头部导航是本次结构性改造的重点。

桌面端策略：

- 保留横向导航。
- 优化站点标题、菜单、登录态之间的排列和留白。
- 保留当前明亮粉色激活态和轻微发光效果，但用更克制、更统一的方式表达。

移动端策略：

- 将菜单改成可折叠或抽屉式结构，避免内容被挤压在单行内。
- 保证站点标题、菜单开关、登录态都能正常显示和点击。
- 增加触控区域大小和交互留白。

目标不是把桌面头部压缩到手机上，而是让移动端拥有属于自己的同风格导航结构。

## 页面级改造范围

### 首页

- 保留轮播、推荐区、主体内容区的基本信息架构。
- 统一内容容器宽度和 section 间距。
- 优化轮播区和推荐区在中小屏下的布局表现。
- 让首页主体双栏在较小断点下自动切单列。
- 通过共享玻璃态面板和间距系统，让首页与全站视觉更加一致。

### 登录页

- 保留当前轻甜、偏粉的氛围感。
- 把固定尺寸的登录卡片改成更弹性的响应式表单面板。
- 优化输入框、按钮、内边距和竖向节奏。
- 使用共享变量和共享面板规则替代登录页自成一套的样式写法。

### 活动页与决议页

- 两者统一纳入同一套列表页壳体结构。
- 保留顶部预览区，但通过统一的头图和卡片规则重写。
- 用响应式容器替代当前大面积固定 padding。
- 让预览卡片和下方列表条目在小屏上能自然折叠。
- 统一状态、时间信息和卡片间距逻辑。

这两个页面本身结构相似，改造后应当明显呈现出“同一类页面”的关系。

### 成员页

- 纳入统一的页面外壳和玻璃态内容容器。
- 优化成员列表的外观，使其与首页和列表页处于同一视觉系统下。
- 提升小屏可读性，必要时通过更合理的字段排布、横向处理方式或密度调整保证可用性。
- 避免靠极小字体来强行塞下所有信息。

### 其他页面片段

如果在改造过程中接触到的局部区块明显破坏整站统一性，可以顺手纳入收口范围。但本次重构仍然聚焦于页面壳体、主要内容区和共享样式基础，不扩散成与当前任务无关的功能性重写。

## 样式组织规范

本次重构不仅改视觉，也会同步整理样式代码的结构和命名方式。

### 全局文件组织

全局样式应按明确职责分层，例如：

- 设计变量层
- 基础/reset 层
- 共享布局工具层
- 共享表面与组件模式层

这些内容可以拆成多个文件，也可以在少量文件中组织，但职责边界必须清楚。

### 组件内样式顺序

Vue 组件中的样式块统一采用以下顺序：

1. 根容器
2. 直接结构子元素
3. 更细的嵌套元素
4. 状态与交互规则
5. 第三方组件覆盖 `:deep(...)`
6. 媒体查询

这样可以明显降低阅读和维护成本。

### 命名策略

逐步替换当前语义过弱的命名，优先使用表达职责的类名，例如：

- `site-header`
- `site-nav`
- `page-shell`
- `content-container`
- `glass-panel`
- `hero-grid`
- `list-card`

不强制项目全面转向严格 BEM，但命名必须足够说明它负责什么。

### 选择器纪律

- 避免在组件中使用过宽的元素选择器去承担本应由类名承担的样式职责。
- 继续使用 scoped 样式，但边界需要更清晰。
- 第三方组件覆盖要集中书写，避免散落。
- 响应式规则尽量靠近它所影响的组件，除非它属于共享布局原语。

## 组件与交互规则

- 桌面端 hover 保留一定表现力，但视觉理解不能依赖 hover 才成立。
- 毛玻璃效果需要兼顾通透感与文字可读性。
- 按钮、链接、卡片点击态要有统一的动效和反馈逻辑。
- 状态文字与元信息尽量使用统一的语义色逻辑。
- 动效保持克制，只保留真正有意义的层次过渡与展开反馈。

## 测试与验证

本次改造完成后至少需要通过以下验证：

- 前端生产构建通过。
- 关键页面在桌面宽度与移动端宽度下完成手动检查。
- 顶部导航在不同页面和不同宽度下可正常使用。
- 共享容器、共享面板影响到的页面不存在明显回归。

因为这次属于样式系统级别重构，所以验证不能只看构建是否通过，也要检查代表性页面行为是否正常。

## 实施顺序

建议按以下顺序实施：

1. 建立全局设计变量、基础样式和共享布局原语。
2. 重构 layout 与 header，先把全站响应式骨架稳定下来。
3. 改造首页与登录页，使其接入共享样式系统。
4. 改造活动页、决议页、成员页，使其统一到相同页面壳体和视觉表面规则中。
5. 在涉及文件中统一类名、样式顺序和响应式组织方式。
6. 运行构建验证并检查关键页面布局。

## 成功标准

当满足以下条件时，可以认为本次重构成功：

- 整站仍然保留原有的粉色二次元识别度。
- 移动端导航和页面排版明显比当前版本更可用。
- 桌面端页面在视觉质感和空间节奏上更统一。
- 共享变量和共享规则替代了大量重复硬编码样式。
- 被修改过的样式文件在命名和结构上明显更清晰。
- 前端构建结果保持可用，没有因样式系统改造引入编译层面问题。
